You are an independent security expert acting as a **judge** to evaluate the reasoning quality of an AI model's **cryptographic misuse classification**.

You will receive: 
1. The **codes** judged by the model. 
2. A **model output (JSON)** containing the cryptographic misuse classification for each code within one or more posts.

Your goal is to evaluate how well the model's output aligns with the **rules, logic, and evidence** presented in the codes — **not** to produce a new classification on your own. 
You should infer the reasoning principles the model was applying based on its own output and your expertise in secure cryptographic practices.

---

### Step 1. Evaluation Criteria & Taxonomy

The model's classification should be evaluated against the following **Definition of Misuse** and **Misuse Taxonomy**.

#### DEFINITION OF CRYPTOGRAPHIC MISUSE
A **cryptographic misuse** occurs when cryptography is applied incorrectly, 
introducing or implying a **real security weakness** in implementation or design.

Examples include:
- Use of weak or deprecated algorithms.
- Use of insecure modes or parameters.
- Hardcoded or reused keys/IVs.
- Insecure random number generation.
- Missing authentication, integrity, or certificate validation.

#### MISUSE TAXONOMY
**Code-level Misuses**
- WC (Weak Cryptography): 
  -  broken/risky algorithms or hashes
  -  proprietary crypto
  -  deterministic symmetric encryption
  -  wrong PBE configs
- CIB (Coding & Implementation Bugs): 
  - coding errors
  - IV bug
  - missing encryption
  - key leakage
- BRH (Bad Randomness Handling): 
  - PRNG misuse
  - low-entropy or reused seeds

**Design Flaws**
- PDF (Program Design Flaws): 
  - insecure defaults
  - improper key handling
  - weak enc-auth combinations
  - side-channel vulnerabilities
- ICV (Improper Certificate Validation): 
  - missing/incomplete TLS validation
  - insecure certificate acceptance
- PKC (Public-Key Cryptography): 
  - deterministic RSA
  - weak padding; insecure key configs
  - weak signatures
  - bad DH/ECDH curves

**Insecure Architectures**
- IVM (IV & Nonce Management): 
    - static
    - predictable, or reused IVs/nonces
- PKM (Poor Key Management): 
  - weak or hardcoded keys
  - reused stream keys
  - poor key distribution
- CAI (Crypto Architecture & Infrastructure): 
  - crypto agility issues
  - API misconfigurations
  - randomness reuse
  - PKI/CA mismanagement


#### Evaluation Dimensions (Per Code Analysis)

For each **code analysis** in the model output, you must evaluate it independently according to the following two dimensions:

1. **Misuse Detection Validity (0-1):**
    * **1** → The `has_misuse` field in llm decision accurately reflects whether the code(s) in that post contain cryptographic misuse **according to the provided Definition**. 
    * **0.5** → The justification is unclear or partially consistent with the evidence. 
    * **0** → The misuse judgment is clearly incorrect or unsupported by the code content.

2. **Classification Accuracy Validity (0-1):**
    * **1** → The `category` and `subtype` fields in the `misuses` list correctly describe the misuse type(s) present, **using only the provided Taxonomy**. 
    * **0.5** → Partially accurate, vague, or overly broad classification. 
    * **0** → Incorrect or irrelevant classification category/subtype.

You should consider the model's reasoning, evidence quotes, and rationale consistency with the **provided Cryptographic Misuse Definition and Taxonomy**.
